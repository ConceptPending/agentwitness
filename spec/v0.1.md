# agentwitness — Event Log Specification v0.1 (draft)

**Status:** Draft. Internal review only — not for external sharing.
**Date:** 2026-05-23
**Editor:** Nick Williamson <nick@nickw.info>
**License:** [CC-BY-4.0](https://creativecommons.org/licenses/by/4.0/)

## 1. Scope

This specification defines the on-disk format for a developer-local,
append-only, signed, hash-chained record of AI coding-agent actions — an
*agentwitness log* — together with the authority manifest that scopes which
keys may sign which actions and the *evidence bundle* used to export portions
of a log for review or verification.

**In scope:**

- Event record structure for actions captured from a coding-agent runtime
  (canonical example: Anthropic's Claude Code)
- Hash-chain linkage between events
- Signing envelope using Ed25519
- Authority manifest format describing keys, scopes, and (single-hop) delegations
- Evidence bundle directory layout
- Canonical serialisation for digest and signature computation
- Trust-anchor expectations
- Versioning and forward-compatibility rules

**Out of scope (deferred):**

- Wire transport — an agentwitness log is a local artefact. Future revisions
  may align with IETF MCPS or ATTP.
- Centralised verification servers; real-time event streaming
- ECDSA P-256 signing (may be added in v0.2 for IETF AAT interop)
- Multi-machine merge / distributed replication
- MCP server interaction for agent self-attestation (post-v0)
- Multi-hop delegation chains beyond a single hop (post-v0)
- Operational policy for content capture beyond the §5.3 hooks

## 2. Threat model

Verbatim with `DIRECTION.md §7`. In short: a signed, hash-chained log proves
that captured events were not modified after capture and that signed actions
trace back to a known key. It does **not** prove completeness in a hostile
local environment, semantic intent, key security, or causation. Completeness
is a process problem (approved configuration, CI enforcement, retained
checkpoints, review policy), outside the scope of this spec.

A separate property — that a signing key corresponds to a specific real-world
person, machine, organisation, or contractor — is not provable from the
bundle alone. See §11 for trust-anchor expectations.

## 3. Identifiers, time, and paths

### 3.1 Time

All timestamps are RFC 3339 strings in UTC with millisecond precision and
the literal suffix `Z`:

```
2026-05-23T14:30:00.123Z
```

Offsets other than `Z` are not permitted in v0.1 (avoids canonicalisation
ambiguity).

### 3.2 Identifiers

- **`session.agentwitness_id`** — opaque identifier assigned by the recorder.
  Format: literal `sess_` prefix plus a 22-character Crockford base32
  (lowercase) random string carrying at least 110 bits of entropy. Stable for
  the lifetime of a recording session.
- **`session.platform_id`** — the agent runtime's own session identifier when
  one is available (Claude Code passes a session ID via hook payloads). Stored
  verbatim. Optional; absent when the runtime does not expose one.
- **`event_id`** — derived. **Full** lowercase hex SHA-256 digest of the
  canonical event body per §7 (64 hex characters). Computed after the event
  body is finalised and before signing.
- **`key_id`** — lowercase hex SHA-256 digest of the raw 32-byte Ed25519
  public key (64 hex characters).
- **`manifest_id`** — lowercase hex SHA-256 digest of the canonical manifest
  body per §9.1 (64 hex characters).

Tools MAY display short prefixes of these identifiers (e.g., the first 12
characters) for human readability, but the canonical form on disk and over
the wire is always the full hex digest.

### 3.3 Paths

File paths are POSIX-style strings. Resolution and matching follow §3.4.

### 3.4 Path normalisation

Before comparison against authority scopes or before storing in an event,
paths are normalised as follows:

1. **Resolution.** Symbolic links are NOT followed during normalisation; the
   logical path the agent invoked is recorded. (Following symlinks would
   silently re-target events outside the project.)
2. **`..` resolution.** Path segments are collapsed lexically (`a/b/../c` →
   `a/c`). Paths whose lexical collapse escapes the project root are stored
   absolute and matched only against absolute scope patterns.
3. **Project root.** When the recorder can identify a project root (Git
   repository root, or a configured root), paths within it are stored
   repository-relative without a leading `/`.
4. **Case sensitivity.** Paths are compared case-sensitively regardless of
   filesystem behaviour. A recorder on a case-insensitive filesystem MUST
   store paths exactly as the agent invoked them.
5. **Encoding.** Paths are UTF-8 byte sequences. Non-UTF-8 paths are stored
   percent-encoded (`%XX`) and matched as such.

Glob semantics in scope patterns:

- `*` — any sequence not containing `/`
- `**` — any sequence including `/`
- `?` — any single character not containing `/`
- A leading `/` anchors the pattern to the project root; otherwise it
  matches at any depth.

## 4. Resources and operations

Events whose `kind` starts with `tool.` describe *resource operations*
rather than a bare list of paths. This lets `blame`, PR review, and policy
enforcement distinguish reads from writes from deletions.

Non-tool events (session lifecycle, prompts, authority updates) do not
carry a `resources` field; see §5 field requirements.

A `resource` object:

```json
{
  "type": "file",
  "op": "write",
  "path": "src/app.ts",
  "before_hash": "<sha256 hex of pre-op content, or null if not pre-existing>",
  "after_hash":  "<sha256 hex of post-op content, or null if deleted>"
}
```

Defined `type` values in v0.1: `file`. Future versions may add `network`,
`process`, `secret`, etc.

Defined `op` values for `type: "file"`:

| op | Semantics |
|---|---|
| `read` | The agent observed the file's contents. `before_hash` present, `after_hash` MUST equal `before_hash`. |
| `write` | The agent modified or created the file. `before_hash` is null if the file did not pre-exist. |
| `delete` | The agent removed the file. `after_hash` is null. |
| `mention` | The agent referenced the path (e.g., in a prompt) without reading it. Both hashes null. |
| `execute` | The agent executed the file (e.g., ran a script). `before_hash` present. |

A single event MAY carry multiple resources (e.g., a `Bash` invocation that
both reads `package.json` and writes `package-lock.json`).

## 5. Event format

An event is a JSON object:

```json
{
  "v": "agentwitness/0.1",
  "id": "<event_id, full 64-char sha256 hex>",
  "prev": "<event_id of previous event, or null for genesis>",
  "session": {
    "agentwitness_id": "sess_xxxxxxxxxxxxxxxxxxxxxx",
    "platform_id": "<runtime-provided session id, or null>"
  },
  "seq": 0,
  "ts": "2026-05-23T14:30:00.123Z",
  "kind": "tool.completed",
  "agent": {
    "platform": "claude-code",
    "model": "claude-opus-4-7",
    "model_version": "claude-opus-4-7-20260101"
  },
  "actor": {
    "signer_key_id": "<key_id of the key that signed this event>",
    "principal_key_id": "<key_id of the principal whose authority backs this action>",
    "delegation": []
  },
  "scope_token": "<manifest_id>:<principal_index>",
  "tool": "Edit",
  "request_id": "<event_id of the corresponding tool.requested event, when applicable>",
  "inputs": {
    "file_path":   { "kind": "json", "hash": "<sha256 hex>", "size": 42 },
    "old_content": { "kind": "text", "hash": "<sha256 hex>", "size": 1280 }
  },
  "resources": [
    { "type": "file", "op": "write", "path": "src/app.ts",
      "before_hash": "<sha256 hex>", "after_hash": "<sha256 hex>" }
  ],
  "outcome": {
    "status": "ok",
    "code": "edit.applied",
    "message": "patched 1 hunk"
  },
  "outputs": {}
}
```

**Field requirements.** The following fields are REQUIRED for every event,
regardless of `kind`:

`v`, `id`, `prev`, `session`, `seq`, `ts`, `kind`, `agent`, `actor`,
`scope_token`, `outcome`.

The fields `tool`, `inputs`, `outputs`, `resources`, and `request_id`
describe tool invocations. They are REQUIRED for events whose `kind`
starts with `tool.` and MUST be omitted for all other kinds. A verifier
encountering one of these fields on a non-tool event MUST reject the
event with `event.unexpected_field`.

Unknown fields MUST be preserved by tools that re-serialise an event for
verification.

### 5.1 Event kinds (two-phase tool lifecycle)

Tool invocations are modelled as a request/response pair. This captures
attempted actions and denials cleanly, and maps to the Claude Code hook
lifecycle (`PreToolUse` → `PostToolUse` / `PostToolUseFailure`).

| Kind | When emitted | Notes |
|---|---|---|
| `session.start` | First event of a session | References the active manifest. |
| `session.end` | Last event of a session (clean shutdown) | Absence indicates abrupt termination. |
| `user.prompt` | User input received | Content hashed by default; raw content not stored. |
| `tool.requested` | Tool invocation requested by the agent | Emitted at `PreToolUse`. |
| `tool.completed` | Tool invocation completed successfully | Emitted at `PostToolUse`. `request_id` references the `tool.requested` event. |
| `tool.failed` | Tool invocation attempted but failed | Emitted at `PostToolUseFailure`. `request_id` set. |
| `tool.denied` | Tool invocation blocked by authority scope | Emitted instead of completion. `request_id` set, `outcome.code = "authority.denied"`. |
| `subagent.start` | Subagent dispatched | Optional in v0.1. Records platform-provided subagent identifier. |
| `subagent.end` | Subagent finished | Optional in v0.1. |
| `agent.decision` | Notable agent step worth recording | Optional in v0.1. |
| `authority.update` | Authority manifest changed mid-session | References the new `manifest_id`. |

Additional kinds may be defined by extensions; unknown kinds MUST be passed
through unchanged by verifiers.

### 5.2 `actor` semantics

- `signer_key_id` — the key whose private half signed this event. **MUST
  equal the `key_id` on the corresponding signature object in `signatures.jsonl`.**
- `principal_key_id` — the key representing the human (or system) on whose
  authority the action is performed.
- `delegation` — in v0.1 either empty (when `signer_key_id == principal_key_id`)
  or a single-element array `[{ "from": "<principal_key_id>", "to": "<signer_key_id>",
  "grant_ref": "<manifest_id>:<principal_index>" }]` representing the
  single-hop delegation that authorised the signer to act on the principal's
  behalf. Multi-hop delegation is deferred to post-v0.

**Verification rule.** For each event:

1. `signature.key_id == actor.signer_key_id`.
2. The signer is authorised by the scope referenced by `scope_token`.
3. If `principal_key_id != signer_key_id`, the `delegation[0].grant_ref` MUST
   resolve to a manifest scope that names the signer as an allowed delegate
   of the principal, valid at the event's `ts`.

### 5.3 Content handling

For events with `kind` starting `tool.`, `inputs` and `outputs` carry
only `{kind, hash, size}` by default. Raw content is NEVER stored inside
the event log. If a deployment opts into raw-content capture, raw content
lives in a sibling content-addressed store (`content/<sha256-hex>` within
the bundle), referenced by hash from the event. This separation lets
bundles export metadata-only by default and lets redaction rules drop
content without invalidating the chain.

#### 5.3.1 Hash semantics

`hash` is always lowercase hex SHA-256, and the bytes hashed depend on `kind`:

| `kind` | Bytes hashed | `size` |
|---|---|---|
| `text` | UTF-8 encoding of the string | Byte length of the UTF-8 encoding |
| `binary` | Raw bytes | Byte length of the raw bytes |
| `json` | RFC 8785 JCS canonicalised JSON, UTF-8 | Byte length of the JCS-canonical form |

A producer that cannot reach JCS-canonical form for a `json` input MUST
downgrade to `kind: "text"` and hash the raw text.

## 6. Hash chain

Events form a singly-linked chain via `prev`:

- The first event in a session is a `session.start` with `prev: null` and
  `seq: 0`.
- Each subsequent event sets `prev` to the previous event's `id` and `seq`
  to the previous `seq + 1`.
- The chain is per-session.

A verifier walks the chain by recomputing each event's `id` from its
canonical body (§7), comparing against the stored `id`, and confirming
that `prev` matches the previous computed `id` in order.

### 6.1 Chain checkpoints

A bundle includes a `chain.json` file that records, per session, the head
`event_id`, the final `seq`, and the time range covered:

```json
{
  "v": "agentwitness/0.1",
  "sessions": [
    {
      "session_agentwitness_id": "sess_...",
      "first_event_id": "<event_id of session.start>",
      "head_event_id":  "<event_id of last event in this bundle>",
      "head_seq": 412,
      "first_ts": "2026-05-23T13:00:00.000Z",
      "last_ts":  "2026-05-23T16:42:01.872Z",
      "manifest_ids": ["<manifest_id>", "..."]
    }
  ],
  "sig": "<base64 detached Ed25519 signature over the canonical chain body with sig absent, by the bundle issuer key>"
}
```

The chain checkpoint is signed independently of the per-event signatures.
This is intentional: per-event signatures give fine-grained non-repudiation;
the checkpoint signature gives a single point of integrity for the whole
session range, and verifies cheaply.

## 7. Canonical serialisation

Canonicalisation uses RFC 8785 — JSON Canonicalization Scheme (JCS):

- Keys sorted lexicographically by Unicode code point
- No insignificant whitespace
- UTF-8 encoding
- ECMAScript-compliant number serialisation

### 7.1 `event_id` derivation

1. Take the event JSON object.
2. Remove the `id` field if present.
3. Canonicalise per JCS.
4. Compute SHA-256 over the canonical bytes.
5. Encode as lowercase hex. The full 64-character digest is `event_id`.
6. Insert `id` into the object.

### 7.2 Event-signature input

The bytes signed for each event are the canonical bytes of the event
**with `id` present**. The signature itself is detached in
`signatures.jsonl` and is never part of the event object.

### 7.3 `manifest_id` derivation and manifest signing

1. Take the manifest JSON object.
2. Remove both `id` and `sig` fields if present.
3. Canonicalise per JCS.
4. Compute SHA-256, lowercase hex; the full digest is `manifest_id`.
5. Insert `id` into the object.
6. Canonicalise the object again — now with `id` present and `sig` absent.
7. Sign those bytes with the issuer's Ed25519 key.
8. Insert `sig` (base64-encoded 64-byte signature) into the object.

Verifiers reverse the process: parse the manifest, save and strip `sig`,
recompute `manifest_id` via steps 2-4 against the body with `id` and `sig`
absent, confirm the stored `id` matches, then verify `sig` over the
canonical body with `id` present and `sig` absent.

## 8. Signing envelope

Signatures are **detached** — stored alongside events rather than embedded
in them — so that the canonical event body and its hash are unaffected by
signature presence or rotation.

Bundle layout (signing portion):

```
log/
  events.jsonl          # one event per line
  signatures.jsonl      # one signature object per line, in the same order
```

A signature object:

```json
{
  "event_id": "<event_id>",
  "key_id": "<key_id>",
  "alg": "ed25519",
  "sig": "<base64-encoded 64-byte Ed25519 signature>"
}
```

The signature covers the canonical bytes produced by §7.2.

**Forward compatibility.** Future versions may add `alg: "ecdsa-p256"` for
AAT interop. Verifiers MUST reject signatures with unknown `alg` values.

**Verifier algorithm (per event).**

1. Parse the event line; extract the stored `id`.
2. Recompute `event_id` per §7.1; compare against stored `id`. Reject on mismatch.
3. Canonicalise the event with `id` present (§7.2).
4. Look up the signature for this `event_id` in `signatures.jsonl`.
5. Confirm `signature.key_id == event.actor.signer_key_id`.
6. Look up the public key for `signature.key_id` in the active manifest.
7. Verify the signature with that public key over the canonical bytes from step 3.
8. Apply the §5.2 verification rules for `actor` and `scope_token`.

## 9. Authority manifest

A manifest declares the keys and scopes valid for a session. Stored as
`manifest.json` in single-manifest bundles or `manifests/<manifest_id>.json`
when a bundle covers multiple sessions or authority changes.

### 9.1 Format (canonical JSON)

```json
{
  "v": "agentwitness/0.1",
  "id": "<manifest_id>",
  "issued_at": "2026-05-23T14:00:00.000Z",
  "expires_at": "2026-05-23T22:00:00.000Z",
  "issuer": "<key_id of issuing key>",
  "project": {
    "name": "myproject",
    "root_hash": "<sha256 of repo HEAD or null>"
  },
  "principals": [
    {
      "key_id": "<key_id>",
      "label": "nick-laptop",
      "public_key": "<base64 of 32-byte Ed25519 public key>",
      "scopes": [
        {
          "allow_tools": ["Edit", "Bash:pytest", "Bash:npm test"],
          "deny_tools":  ["Bash:terraform*", "Bash:kubectl*"],
          "allow_paths": ["src/**", "tests/**"],
          "deny_paths":  [".env", "**/secrets/**"],
          "allow_delegates": []
        }
      ]
    }
  ],
  "sig": "<base64 signature, see §7.3>"
}
```

### 9.2 Authoring format (TOML, non-canonical)

The canonical, signed, transported form of a manifest is JSON per §9.1.
For human authoring, the recorder accepts a TOML representation with
identical field semantics; the recorder converts TOML → JSON via JCS and
signs the JSON form. The TOML form is **not** part of the wire format and
MUST NOT be relied on by verifiers.

### 9.3 Evaluation rules

- `allow_tools` and `deny_tools` match the event's `tool` field. Bash
  variants are matched as `Bash:<argv[0]>` (e.g. `Bash:pytest`); globs
  allowed.
- `allow_paths` and `deny_paths` match every entry in the event's
  `resources[].path`. The action is denied if any resource fails.
- An action is permitted iff (a) at least one principal scope matches *all*
  required `allow_*` rules, (b) no `deny_*` rule matches, and (c) the
  evaluation time is within `[issued_at, expires_at]`.
- A `tool.requested` event whose action would not pass evaluation MUST be
  followed by `tool.denied` rather than `tool.completed`, with the same
  `inputs` (hashed) and `outcome.code = "authority.denied"`.

### 9.4 Bash classification is best-effort

`Bash:<argv[0]>` matching is **not** a strong security boundary. Commands
like `sh -c`, `python -c`, `npx`, `make`, `npm run`, wrapper scripts, and
`sudo` can hide powerful actions behind a benign-looking `argv[0]`. v0.1
manifests SHOULD treat Bash scopes as advisory and pair them with stricter
process-level controls (separate sandboxing, OS-level allowlists, container
isolation). Future revisions may add finer classification.

### 9.5 Delegation (single-hop, v0.1)

A scope's `allow_delegates` lists `key_id`s permitted to act on the
principal's behalf. The delegate's signed events carry
`actor.principal_key_id` equal to the principal and `actor.signer_key_id`
equal to the delegate, with `delegation[0]` filled per §5.2.

Multi-hop delegation (a delegate further delegating to a third key) is
deferred to post-v0; v0.1 verifiers MUST reject `delegation` arrays of
length > 1.

## 10. Evidence bundle layout

An evidence bundle is a directory or tar archive:

```
bundle/
  manifest.json              # single-manifest case
  manifests/                 # multi-manifest case
    <manifest_id>.json
  events.jsonl
  signatures.jsonl
  chain.json                 # per-session head + signed checkpoint
  summary.md                 # human-readable summary (generated)
  diff-map.json              # machine-readable file → events index
  verify.json                # output of `agentwitness verify` against the bundle (REPORT, not proof)
  content/                   # optional, only when raw-content capture is on
    <sha256-hex>
    ...
```

`verify.json` is a record of one verifier's findings. It is never treated
as proof of anything; any party reviewing a bundle should re-run
verification themselves.

Bundles MAY be packaged as `.tar.gz` for transport. A bundle is internally
verifiable offline given only its contents plus the public keys named in
its manifests.

## 11. Trust anchors

A bundle proves **internal cryptographic consistency**: the event chain
is intact, signatures are valid, scopes match, and manifests verify against
their issuers. It does **not** prove **external identity** — that a key
belongs to a particular person, machine, or organisation.

Establishing external identity is the responsibility of a *trust anchor*
outside the bundle. Acceptable trust anchors include:

- **Pinned key.** Recipient holds a copy of the issuer's public key, obtained
  out of band (e.g. exchanged in person, posted on a known personal page).
- **Organisation key registry.** A company maintains a signed registry of
  approved keys per employee/contractor; the recipient verifies the bundle's
  issuer against that registry.
- **GitHub identity binding.** A key fingerprint is published in the issuer's
  GitHub profile or as a verified attestation; the recipient cross-checks.
- **Sigstore-style transparency.** A bundle issuer obtains a Sigstore
  certificate binding their key to an OIDC identity; the recipient verifies
  the certificate.
- **SSO / IdP export.** The recipient's IdP maps a key to an internal
  identity, and the recipient enforces that mapping.
- **Customer-supplied allowlist.** A receiving organisation pins acceptable
  issuer keys directly in their CI verifier configuration.

agentwitness v0.1 does NOT mandate any particular trust anchor. It surfaces
`key_id` and `issuer` clearly so any of the above approaches can be layered
on top. Without a trust anchor, a recipient knows only that *some* key
signed a self-consistent bundle.

## 12. Versioning policy

Every event and manifest carries `v: "agentwitness/<major>.<minor>"`.

- Verifiers MUST reject artefacts whose major version they do not understand.
- Within a major version, fields may be added but not removed or repurposed.
- Patch revisions of a minor version are documentation-only and produce no
  wire change.

## 13. Interop with adjacent standards

The agentwitness spec is independent of the IETF agent-attestation drafts
but is deliberately migration-friendly:

| Adjacent standard | Relationship |
|---|---|
| IETF AAT (`draft-sharif-agent-audit-trail`) | Same canonicalisation (RFC 8785 JCS), same SHA-256 chaining, similar event shape. AAT uses ECDSA P-256; agentwitness uses Ed25519 in v0.1. AAT-compatible export may be added in v0.2 by emitting both signature algorithms. |
| IETF AIVS (`draft-stone-aivs`) | Same hash-chain primitive; AIVS already permits Ed25519. Bundle → AIVS translation should be straightforward. |
| IETF ATTP (`draft-sharif-attp-agent-trust-transport`) | Wire-protocol concern; ATTP bakes a hash-chained audit log into transport. agentwitness logs could be emitted *into* an ATTP session if ATTP gains adoption. |
| IETF klrc-aiagent-auth (`draft-klrc-aiagent-auth`) | Identity/authorisation layer, complementary not competing. A future revision may accept klrc authority assertions as `scope_token` values. |
| IETF MCPS (`draft-sharif-mcps-secure-mcp`) | MCP wire signing — orthogonal to agentwitness; would feed verified MCP messages into agentwitness as a recorder upstream. |
| DSSE | The §8 envelope is intentionally simpler than DSSE. DSSE has cross-ecosystem traction; v0.1 stays minimal and translates losslessly to DSSE later. |
| W3C Agent Identity Registry Protocol | Watch for DID/VC vocabulary that should appear in `manifest.principals`. |

A `spec/interop.md` document will track field-level translation tables as
these drafts evolve. v0.1 makes no formal interop guarantees.

## 14. Open questions

Deliberate v0.1 decisions to revisit, not bugs:

- **Multi-hop delegation.** Single-hop only in v0.1; nested delegation is
  the natural post-v0 extension. The `actor.delegation` field has space but
  the verifier currently rejects length > 1.
- **`inputs.kind` granularity.** Currently `text | binary | json`; may add
  a `mime` field in v0.2 if downstream consumers need it.
- **DSSE adoption.** The envelope in §8 is minimal and translates to DSSE
  later if cross-ecosystem alignment turns out to matter more than envelope
  simplicity. Decision deferred to v0.2.
- **Time precision.** Millisecond; revisit if any downstream consumer asks
  for microsecond.
- **Canonicalisation of `null` vs absent fields.** JCS handles this, but
  the spec should add explicit examples before any external review.
- **Resource types beyond `file`.** `network`, `process`, `secret`, `env`
  are all reasonable v0.2 additions.
- **Subagent delegation semantics.** When a parent agent dispatches a
  subagent that signs its own events, what is the right relationship
  between `subagent.start` and the subagent's `actor.principal_key_id`?
  Probably: principal stays the human; signer becomes the subagent's
  ephemeral key; delegation chain captures the parent → subagent hop. Pin
  this down before any post-v0 multi-hop work.
